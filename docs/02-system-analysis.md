## 1. 分析目的與原則

本文件將已核准的專案計畫轉換成可驗收的系統需求、Use Case、資料治理規則與 RAG 評估規格，作為後續系統設計（SD）的需求基線。

本階段只定義「系統必須做什麼」與「如何判定做對」，不在此鎖定 LLM、Embedding、Vector DB、後端框架、UI 框架或部署方式。這些技術決策須於 SD 階段以 ADR 確認。

分析遵循以下原則：

- 來源可追溯：非拒答答案必須能回到來源 URL、版本或資料時間。
- 版本有意識：新舊資料不可無提示混用；無法判定適用版本時不得假裝確定。
- 證據優先：檢索證據不足、超出 MVP 範圍或來源衝突時，系統應拒答或明確標示不確定性。
- 結構化優先：精確數值與欄位查詢優先使用結構化資料，不以生成模型自行計算或補值。
- Local-first：核心流程不可依賴付費 API 或持續付費服務。
- 可重現：需求、測試題庫、資料來源規則與評估結果都應能在本機重現。

## 2. 系統定位、角色與邊界

### 2.1 系統定位

系統是一套服務繁體中文《原神》玩家的本機 RAG 知識助手。使用者以自然語言提問，系統依問題類型選擇結構化查詢或文件檢索，產生附來源、版本／時間資訊的回答；若證據不足或衝突，則說明限制並拒答或降級為不確定回答。

### 2.2 角色（Actors）

| 角色 | 目標／責任 | 是否為 MVP 使用者 |
|---|---|---:|
| 玩家（User） | 以繁體中文查詢角色、武器、素材、任務、世界觀及版本資訊 | 是 |
| 資料維護者（Maintainer） | 手動或依程序執行來源擷取、驗證、正規化與索引更新 | 是（專案擁有者兼任） |
| 評估者（Evaluator） | 執行 50 題題庫、檢查人工標註與 Release Gate | 是（專案擁有者兼任） |
| 官方公告來源 | 提供版本更新、修正與已知問題 | 外部來源 |
| genshin-db | 提供角色、武器、技能、素材等結構化資料 | 外部來源 |
| Fandom Wiki | 提供任務、角色故事、世界觀與補充敘述 | 外部來源 |
| 本機模型執行器 | 依檢索證據生成回答或拒答 | 系統外部相依 |

### 2.3 MVP 納入範圍

| 類別 | 必須支援的內容 |
|---|---|
| 角色 | 基本資料、技能、命座、角色故事 |
| 武器 | 名稱、類型、稀有度、數值及效果 |
| 素材 | 名稱、類型、用途；不含取得方式 |
| 任務與世界觀 | 任務摘要、人物關係、地區及背景設定；回答需支援劇透提示 |
| 版本資訊 | 更新內容、調整、修正及已知問題 |

### 2.4 MVP 明確排除

- 素材取得方式、採集位置及路線規劃。
- 配隊、聖遺物及抽卡建議。
- 個人帳號、角色庫或遊戲紀錄分析。
- 測試服、洩漏或尚未正式發布的資料。
- 24/7 公開服務及商業化營運。

超出範圍的問題不得由模型自行擴張成產品功能；應回覆目前支援範圍與可行的替代查詢。

## 3. 主要使用情境（Use Cases）

### UC-01：查詢 MVP 範圍內的知識

**目的**：玩家以繁體中文取得可追溯的角色、武器、素材、任務、世界觀或版本回答。

**前置條件**：資料來源已通過最低驗證，索引／結構化資料可讀，系統能保存查詢與引用結果。

**主要流程**：

1. 玩家輸入自然語言問題。
2. 系統辨識語言、問題類型、實體名稱、版本／時間限制與是否包含劇透。
3. 系統依類型執行結構化查詢或文件檢索，並套用來源權威性與版本規則。
4. 系統檢查證據是否足以支持答案。
5. 系統以繁體中文輸出答案、來源連結、適用版本／資料時間與必要限制。

**替代流程**：問題包含多個子問題時，系統應分段回答；其中任一子問題證據不足時，只拒答該子問題，不得用其他子問題的證據補齊。

**成功條件**：答案事實均可由列出的證據支持，且非拒答答案附來源率達 100%。

### UC-02：精確數值或欄位查詢

**目的**：玩家查詢武器數值、稀有度、技能倍率或其他可結構化表示的內容。

**主要流程**：

1. 系統將問題分類為精確欄位查詢。
2. 系統對實體名稱與別名做正規化。
3. 系統從結構化資料取得欄位與適用版本。
4. 若欄位缺失、版本不明或同一欄位有衝突，系統顯示限制，不用生成內容補值。
5. 輸出欄位值、單位／條件、版本與來源。

**成功條件**：輸出值與預期資料一致；缺值時正確拒答率納入評估。

### UC-03：版本更新或版本差異查詢

**目的**：玩家查詢某次版本更新、調整、修正或新舊版本差異。

**主要流程**：

1. 系統抽取版本號、日期或「目前／舊版本」限制。
2. 優先檢索官方公告，再以結構化資料或補充來源交叉確認。
3. 回答中明確標示適用版本、公告日期與資料擷取時間。
4. 若問題要求的版本不存在於資料集，系統說明缺少該版本資料。

**成功條件**：不得把不同版本數值或敘述無提示地合併；版本不明時必須標示不確定性。

### UC-04：來源衝突處理

**目的**：不同來源對同一事實提供不一致內容時，避免輸出沒有依據的單一結論。

**主要流程**：

1. 系統以實體、欄位／主張及適用版本建立可比較的 claim。
2. 系統依來源權威性、發布日期與擷取時間比對內容。
3. 若官方公告可明確定案，採官方內容並列出必要補充來源。
4. 若仍無法定案，列出衝突摘要、來源與版本，拒絕作出單一肯定結論。

**成功條件**：衝突題不得被評為無警告的正確肯定答案；回答需指出衝突或不確定原因。

### UC-05：資料不足、超出範圍或拒答

**觸發條件**：問題超出 MVP、要求洩漏／測試服資料、沒有足夠證據、實體無法辨識，或來源衝突無法解決。

**回應要求**：

- 明確指出拒答原因，不得捏造答案或引用不存在的來源。
- 若可行，說明目前支援的範圍或建議使用者補充的版本／名稱。
- 若只有部分子問題可回答，將可回答與不可回答部分分開。
- 拒答本身仍應保存分類、原因與所檢查的證據，供評估使用。

### UC-06：來源資料匯入與驗證

**目的**：維護者依來源策略建立可追溯的資料快照或索引。

**主要流程**：

1. 選擇來源與擷取範圍，記錄擷取時間及來源版本／發布日期。
2. 驗證來源可存取性、格式、必要欄位、重複資料與授權註記。
3. 正規化名稱、別名、版本、日期、語言與實體類型。
4. 產生結構化資料與可檢索文件單位，保留來源關聯。
5. 只有通過驗證的資料才可進入索引；失敗項目列出錯誤並停止該批次發布。

**成功條件**：任一可回答事實都能追溯至來源 URL、原始發布資訊與擷取時間。

### UC-07：執行 RAG 評估與 Release Gate

**目的**：以固定題庫分開檢查檢索品質、生成品質、引用完整性與拒答行為。

**主要流程**：

1. 載入版本化題庫與對應的必要事實、版本及來源。
2. 以固定設定執行檢索與回答，保存回答、證據、引用與評估結果。
3. 先計算 Retrieval 指標，再計算答案正確性、Groundedness、拒答與來源指標。
4. 以人工複核處理自動評估不確定的題目。
5. 未達任一 Release Gate 時不得標記 MVP 完成，並建立調整或範圍變更事項。

## 5. 非功能需求（Non-functional Requirements）

### NFR-COST：成本

- 核心功能不得依賴付費 API 或需付費才能持續運作的服務。
- 外部服務若作為選配展示，失效不得影響本機核心流程。
- 月度預算上限為 NT$0；任何付費相依都需 Change Request 與重新核准。

### NFR-REPRO：可重現性

- 新環境可依 README 建立並執行本機 Demo。
- 資料擷取設定、正規化規則、索引建立、評估題庫與執行參數應版本化。
- CI 使用 Mock／Fixture，不因外部來源或模型服務不可用而變成不可重現。

### NFR-MAINT：可維護性

- 擷取、驗證、正規化、結構化儲存、檢索、生成、引用與 UI 應保持可替換邊界。
- 來源規則、拒答規則與評估題庫應能獨立更新，不需修改所有業務程式碼。
- 需求、設計決策與重大範圍變更以文件或 Change Request 留存。

### NFR-PRIV：隱私與安全

- MVP 不收集遊戲帳號、登入資訊、個人資料或遊戲紀錄。
- 日誌不得保存 API 金鑰、Token、密碼或可識別個人資料。
- 本機設定與秘密不得提交 Git；應提供不含秘密的 `.env.example` 或等價說明。

### NFR-OBS：可觀測性與追溯

- 每次回答至少可追溯到查詢 ID、回答分類、檢索證據、引用、資料版本／時間與評估結果。
- 失敗匯入、空檢索、衝突、拒答與模型錯誤應有可診斷的錯誤類型。
- 日誌保存期限與敏感欄位遮罩規則於 SD 階段確認；在此之前不得假設永久保存。

### NFR-PERF：效能（待 SA／SD 定案）

本計畫尚未核准固定回應時間或資源門檻。SA 只要求後續實測並記錄 CPU、RAM、VRAM、索引大小、檢索時間、模型生成時間與端到端時間；具體 Release Gate 由 SD／原型測試提出並核准。

## 6. 資料來源與治理規則

### 6.1 第一版來源優先級

| 優先級 | 來源 | 主要用途 | 計畫更新原則 |
|---:|---|---|---|
| 1 | [HoYoLAB 官方公告](https://www.hoyolab.com/official/2/notices) | 版本更新、修正、已知問題 | 新版本公告發布後 7 天內更新 |
| 2 | [genshin-db](https://github.com/theBowja/genshin-db) | 角色、武器、技能、素材等結構化資料 | 每月檢查更新 |
| 3 | [Genshin Impact Fandom Wiki](https://genshin-impact.fandom.com/wiki/Genshin_Impact) | 任務、角色故事、世界觀及補充說明 | 每月檢查更新 |

更新週期是規劃基準，不代表已完成自動排程；實際擷取介面、robots／API 限制與人工匯入程序屬 SA／SD 待定事項。

### 6.2 來源治理最低欄位

每個來源文件或結構化資料批次至少應保存下列概念欄位；欄位名稱與實體表設計由 SD 定案：

| 欄位 | 用途 |
|---|---|
| `source_id`／`source_kind` | 識別來源及來源類型 |
| `source_url` | 對外引用與追溯 |
| `title` | 顯示文件或公告標題 |
| `published_at` | 原始發布日期／時間（若來源提供） |
| `retrieved_at` | 本機擷取日期／時間 |
| `game_version` | 適用遊戲版本；未知時保留未知狀態 |
| `locale` | 語言與地區 |
| `license_note`／`rights_note` | 授權、署名及權利處理註記 |
| `content_hash` | 偵測內容變更與重複匯入 |

### 6.3 正規化與版本規則

- 名稱、別名、繁簡差異、大小寫與常見拼寫應透過可版本化的字典或規則正規化。
- 正規化不得覆蓋來源原文；原文、正規化值與來源關聯需可分別追溯。
- 每個可回答主張應能關聯到實體、欄位／主張鍵、來源、適用版本與擷取時間。
- 同一主張在不同版本可同時存在；回答必須根據問題版本選擇，不得以最新值覆蓋歷史值。
- 無法判斷版本或來源時間時，回答需顯示限制；不得假設為目前版本。

### 6.4 衝突處理規則

1. 先以 HoYoLAB 官方公告判定正式版本更新、修正與已知問題。
2. 再以 genshin-db 的結構化資料確認可精確表示的欄位。
3. 最後使用 Fandom Wiki 補充任務、故事與世界觀敘述。
4. 來源發布時間較新不會自動勝過較高權威來源；權威性與適用版本需一併考量。
5. 若仍有無法消解的衝突，保存各主張、來源與版本，回答顯示衝突並拒絕單一肯定結論。

### 6.5 授權與保存限制

本文件沿用計畫書的治理方向：Fandom 內容需依其授權保留署名、原文連結與相同方式分享要求；genshin-db 程式碼與遊戲資料的權利需分開判斷；HoYoLAB／HoYoverse 素材僅在非商業個人專案與適用條款範圍內使用。實際抓取方法、robots、API 限制、保存量與發布方式在 SA／SD Review 前不得視為已核准。

## 7. 查詢分類、證據與回答契約

### 7.1 查詢分類

系統至少應區分：

| 類型 | 主要路徑 | 典型例子 |
|---|---|---|
| 結構化欄位 | 正規化實體 → 結構化查詢 → 引用 | 武器類型、稀有度、技能數值 |
| 敘述性知識 | 查詢分類 → 文件檢索 → 證據整合 | 任務摘要、角色故事、地區背景 |
| 版本資訊 | 版本／日期解析 → 官方優先檢索 | 某版本調整、修正、已知問題 |
| 複合問題 | 拆分子問題 → 分別判定證據 | 同時詢問角色故事與數值 |
| 拒答／超出範圍 | 範圍判定 → 原因與替代說明 | 配隊建議、測試服或取得路線 |

### 7.2 證據要求

- 每個非拒答答案的主要事實都必須能對應至少一個列出的證據單位。
- 精確數值必須能追溯到結構化欄位或明確的權威來源，不得由模型自行估算。
- 證據來自不同版本時，回答需分別標示版本，不得無提示拼接。
- 檢索結果為空、證據互相衝突或證據與問題實體不一致時，觸發拒答／不確定流程。
- 本階段不預設模型信心分數作為唯一門檻；信心、Top-k、reranking 與 context 長度於 SD 實測與 ADR 決定。

### 7.3 回答輸出契約（概念）

每次回答至少應能表達下列資訊；實際 API／UI schema 在 SD 定案：

```text
answer_text: 繁體中文回答或拒答說明
answer_status: answered | uncertain | refused | error
query_category: structured | narrative | version | composite | out_of_scope
citations: [{ source_url, title, source_kind, published_at?, retrieved_at?, game_version? }]
evidence_summary: 支持答案的主張／文件摘要
applies_to_version: 明確版本、版本未知或多版本分段
uncertainty_reason?: 證據不足、衝突、超出範圍等原因
spoiler_notice?: 任務／世界觀內容的劇透提示
```

`answer_status=answered` 時，`citations` 不得為空；`uncertain` 或 `refused` 時，需填寫可理解的原因。`error` 只表示系統故障，不得冒充資料拒答。

## 8. 驗收題庫與評估規格

### 8.1 題庫規模與組成

- 第一版共 50 題：40 題可回答、10 題應拒答。
- 每題由人工確認預期答案、必要事實、適用版本與正確來源。
- 題庫需覆蓋 MVP 類別與查詢類型，並包含精確欄位、敘述、版本、衝突、別名及拒答情境。
- 題庫與 fixture 應版本化；新增題目不得任意改寫既有題目的評分標準。

建議的 40 題可回答題目配額與 10 題拒答題目細分，屬待 SA Review 的提案，不是已核准的硬性分配：

- 可回答題：依角色、武器、素材、任務／世界觀、版本資訊與複合查詢分配。
- 應拒答題：依超出範圍、資料不足、版本未知、來源衝突、測試服／洩漏或實體無法辨識分配。

### 8.2 題目欄位契約

| 欄位 | 必填 | 說明 |
|---|---:|---|
| `case_id` | 是 | 穩定且唯一的題目 ID |
| `question_zh_tw` | 是 | 使用者原始繁中問題 |
| `category` | 是 | 角色、武器、素材、任務、世界觀、版本或複合 |
| `query_type` | 是 | structured、narrative、version、composite 等 |
| `answerability` | 是 | answerable 或 refuse |
| `expected_answer` | 可回答題必填 | 人工確認的預期答案或必要答案骨架 |
| `required_facts` | 是 | 評分時必須出現或支持的事實 |
| `expected_sources` | 可回答題必填 | 可接受的來源 URL／來源類型 |
| `game_version` | 是 | 適用版本、版本範圍或 unknown |
| `refusal_reason` | 拒答題必填 | out_of_scope、insufficient_evidence、conflict 等 |
| `spoiler_level` | 是 | none、notice 或 explicit 等待定枚舉 |
| `notes` | 否 | 人工複核、別名或特殊評分說明 |

### 8.3 指標與 Release Gate

| 指標 | 定義（SA） | MVP Gate |
|---|---|---:|
| 回答正確率 | 可回答題中，必要事實與預期答案一致的比例 | ≥ 90% |
| Retrieval Recall@5 | 必要證據出現在前 5 個檢索結果的比例 | ≥ 90% |
| 引用支持答案率／Groundedness | 回答主張能由列出證據支持的比例／題目通過率 | ≥ 95% |
| 無資料正確拒答率 | 應拒答題中正確拒答或標示不確定的比例 | ≥ 90% |
| 非拒答答案附來源率 | 所有非拒答回答具有效來源的比例 | 100% |

指標應分開報告檢索與生成品質；自動評估不得取代人工複核。若指標未達門檻，需記錄失敗題目、可能原因、調整方案與是否提出範圍 Change Request。

### 8.4 評估輸出

每次評估至少產出：題庫版本、程式／索引版本、模型設定摘要、每題回答、檢索結果、引用、指標、人工複核標記、失敗分類與執行時間。報告不得保存金鑰或個人資料。
