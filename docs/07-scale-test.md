# 規模測試：語料放大五倍會發生什麼（T37）

> 執行日期：2026-09-02。所有數字都是實測。

在決定要不要把三十幾個版本公告全部匯入之前，先用五個版本量一次。目的不是涵蓋
範圍，是取得「規模上升時檢索怎麼變」的資料——那是先前完全沒有的東西。

## 1. 做了什麼

匯入 5.1、5.2、5.3、5.4、5.5 五份版本公告，章節 locator 由標題自動產生
（每個標題一節，`end` 指向下一個標題）。

| | 之前 | 之後 |
|---|---:|---:|
| 來源文件 | 9 | 14 |
| 切塊 | 18 | **89** |
| 索引建立時間 | — | 9.3 秒 |
| 68 題評估耗時 | — | 2 分 14 秒 |

## 2. 沒有變差的部分

三項機器指標在 89 個切塊下完全不變：

| 準則 | 18 切塊 | 89 切塊 |
|---|---:|---:|
| Retrieval Recall@5 | 100% (58/58) | **100% (58/58)** |
| 無資料正確拒答率 | 100% (10/10) | **100% (10/10)** |
| 非拒答答案附來源率 | 100% (58/58) | **100% (58/58)** |

退回模板的仍然是同樣兩題。守門案例也都還成立：

- 「納塔的火神是誰？」→ `insufficient_evidence` 拒答、0 筆引用
- 「迪盧克是什麼元素？」（語料沒有的實體）→ 拒答

## 3. 變差的部分，以及一個不能再迴避的結論

### 3.1 相似度門檻的分離性消失了

先前 `DOCUMENT_MIN_SCORE` 之所以能設，是因為可回答的題目與語料答不出來的題目在
分數上分得開。放大之後不成立：

| | 18 切塊（T36） | 89 切塊（本次） |
|---|---|---|
| 可回答題的分數範圍 | 0.532 – 0.795 | **0.438 – 0.712** |
| 「納塔的火神是誰？」（答不出來） | 0.410 | **0.504** |
| 兩者是否分得開 | 是，間隙約 0.12 | **否，完全重疊** |

答不出來的那題現在得 0.504，落在可回答題目的區間**中間**。

**沒有任何門檻值能同時保住所有可回答的題目、又擋掉那一題。** 調高會犧牲
Recall，調低沒有意義。

這不是參數沒調好，是**這個機制到頂了**：語料越大，最近的不相關切塊就越接近最難
的相關切塊。門檻能擋住的只有「明顯在講別件事」，而那個空間隨資料量縮小。

### 3.2 那為什麼「納塔的火神是誰？」還是拒答了

因為擋住它的**已經不是門檻**，是 [`03-system-design.md` §9.3.1](03-system-design.md)
那個檢查：模型讀完證據後自己說「證據中沒有提到」，系統把那句話當成拒答而不是答案。

換句話說，目前系統在這件事上的正確行為**完全依賴模型自述**。模型沒察覺的時候，
沒有任何東西會發現。

### 3.3 版本總覽的答案品質掉了

T34 讓版本總覽取整份公告。在人工挑過章節的 5.0／2.1 上，那產生了條理分明的答案。
自動產生 locator、涵蓋整份公告（13–18 節）之後，答案開頭變成瑣事：

- 「5.3版本更新了哪些內容？」→ 開頭是**胡桃的語音新增**
- 「5.5版本新增了什麼角色？」→ 開頭是**信件珍藏盒增加搜尋功能**

模型拿到 9000 字、十幾節等權重的內容，就照著看到的順序寫。整份公告餵進去解決了
「證據不足」，但沒有解決「哪一段才是讀者要的」。

`versionDocumentMaxChunks` 目前是 24，本次最大的 5.5 是 18 節，還沒觸頂——所以
這個問題**不是上限擋掉的，是上限還沒擋到**。

## 4. 結論與建議

1. **不要調門檻。** 沒有可用的值，本文件 §3.1 是證據。
2. **把門檻的定位改寫。** 它是便宜的第一道過濾，不是正確性的保證——
   `03-system-design.md` §9.3 目前的寫法高估了它。
3. **[#65](https://github.com/frobel0520/Genshin-Impact-RAG-Helper/issues/65)
   （證據涵蓋度檢查）從「值得做」變成「擋在路上」。** 在它做完之前，
   繼續灌資料會讓系統在已經量到的那個方向上變差。
   **（2026-09-04 更新：做完了，但只能記錄不能執行——見 §5。）**
4. **版本總覽需要章節選擇，不是全取。** 這是 T34 的下一步，也是 §3.3 的直接後果。

### 這批資料要不要留

留著，語料就從 18 個切塊變成 89 個，而剛完成的 58 題評分描述的是 18 個切塊的系統，
會立刻失效。

**建議先不要留**：先做 #65，再把資料加回來，那時候才有東西能在資料變多時保護正確性。
本文件的量測結果不會因為資料被移除而失效——數字已經在這裡了。

**（2026-09-04 更新：#65 做完了，但它不是那個東西。加回來的前提還沒滿足——見 §5.4。）**

## 5. #65 做完了，結論不是「擋住了」（T35）

> 執行日期：2026-09-04。語料已退回 18 切塊（見 §4），本節數字都在該語料上量的。

§4 第 3 點把 [#65](https://github.com/frobel0520/Genshin-Impact-RAG-Helper/issues/65)
列為「擋在路上」，理由是門檻到頂之後需要別的東西保護正確性。檢查做出來了，
**它抓得到門檻抓不到的那一題，但也會誤殺可回答的題目**，所以預設只記錄不執行。

### 5.1 作法

寫答案之前，把問題與政策階段核可的證據交給同一個模型（`qwen2.5-coder:14b`，
temperature 0，seed 1），只要 YES 或 NO。判不出來（逾時、錯誤、回覆不是 YES／NO）
一律照常回答。設計細節見 [`03-system-design.md` §9.5](03-system-design.md)。

### 5.2 打開執行之後，58 題題庫少了一題

| 準則 | 關閉（預設） | 打開 `ENFORCE_COVERAGE` |
|---|---:|---:|
| Retrieval Recall@5 | 100% (58/58) | **98.28% (57/58)** |
| 無資料正確拒答率 | 100% (10/10) | 100% (10/10) |
| 非拒答答案附來源率 | 100% (58/58) | 100% (57/57) |
| 非拒答題數 | 58 | **57** |

掉的是 `case:kujou-sara-role`（「九條裟羅在稻妻擔任什麼職務？」）。它的證據裡逐字
寫著「天領奉行的將領」，檢查仍然判 NO，答案被收走、引用歸零。

**那不是邊界案例，是誤判。** 而且方向最糟：讀者失去一個他本來拿得到的正確答案，
而拒答看起來跟「系統很謹慎」沒有兩樣，沒有人會去查。

### 5.3 換 prompt、換 seed 都沒有救回來

四個手工修剪過證據的案例（每題只餵一段，比實際管線嚴苛），兩個 system prompt：
A 是現行的極簡版，B 明寫「預設 YES，只有證據完全沒提到才 NO，用詞不同不算沒提到」。

| 問題 | 應為 | prompt A | prompt B |
|---|---|---|---|
| 九條裟羅在稻妻擔任什麼職務？ | YES | **NO** | **NO** |
| 納塔的火神是誰？ | NO | NO | NO |
| 瑪拉妮是什麼元素？ | YES | YES | YES |
| 瑪拉妮是做什麼的？ | YES | **NO** | **NO** |
| | | 2/4 | 2/4 |

seed 1 與 seed 20260902 兩組跑出**完全相同**的表。

所以這不是抽樣雜訊，是一個可重現的形狀：**問「擔任什麼職務／是做什麼的」，證據用
自己的話描述了那個身分但沒有重複問題的用詞，檢查就判 NO。** 提示模型「用詞不同
不算」沒有改變任何一格。

（實際管線裡「瑪拉妮是做什麼的？」沒有出事——它拿到的證據不只一段。§5.2 只掉一題，
不是四題裡掉兩題。）

### 5.4 結論

1. **預設不執行。** `ENFORCE_COVERAGE` 預設 false，判 NO 時記一筆
   `evidence_may_not_cover_question`，答案照發。開關留著是為了讓人自己量取捨。
   實測 58 題只產生 **1 筆**這樣的記錄，就是 §5.2 那一題；三項機器指標全部回到
   100%（58/58、10/10、58/58），該題仍照常回答並附引用。
2. **§4 第 3 點要改寫。** #65 做完了，但它**沒有**變成「資料變多時保護正確性」的
   那個東西。§4 的建議（先做 #65 再把五個版本加回來）**不再成立**——現在把資料加
   回來，多的仍然只是一筆日誌，不是一道閘門。
3. **下一步不是調 prompt。** 兩個 prompt、兩個 seed、同一張表，說明問題不在措辭。
   要嘛換更適合做判別的模型，要嘛回到 #65 原本的路線（抽取問題面向再比對），
   兩者都比本次的成本高一個量級。

```
GET https://bbs-api-os.hoyolab.com/community/post/wapi/getNewsList?gids=2&page_size=30&type=1
    header x-rpc-language: zh-tw
    分頁用回應裡的 last_id
```

章節 locator 本次是自動產生的：把純文字裡形如 `〓…〓` 或 `一、…` 的標題各切成一節，
`end` 指向下一個標題，只保留在文章中唯一出現的標題。**這正是 §3.3 那個問題的來源**
——自動切出來的十幾節等權重，模型會照順序寫而不是照重要性寫。加回來的時候應該
連同章節選擇一起處理，而不是重複這次的作法。
